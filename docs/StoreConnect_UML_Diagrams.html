5. Order Status State Machine

Valid order status transitions. The system enforces these rules — no invalid transitions are allowed.

%%{init: {'theme': 'default', 'state': {'useMaxWidth': true}}}%% stateDiagram-v2 [*] --> CREATED : Customer places order CREATED --> CONFIRMED : Inventory validated\nand reserved CREATED --> CANCELLED : Customer cancels CONFIRMED --> PROCESSING : Store begins\nfulfillment CONFIRMED --> CANCELLED : Customer cancels\nStock released PROCESSING --> READY : Items prepared\nfor pickup READY --> DELIVERED : Customer\nreceives order PROCESSING --> CANCELLED : Fulfillment issue\nStock released DELIVERED --> [*] CANCELLED --> [*]
Valid transitions: CREATED → CONFIRMED → PROCESSING → READY → DELIVERED. Cancellation is allowed from CREATED, CONFIRMED, or PROCESSING (with stock release). Orders that are READY or DELIVERED cannot be cancelled.

4b. Relational Database Model (ERD)

Database schema entities, primary keys (PK), foreign keys (FK), and cardinalities (1:1, 1:N, M:N) for PostgreSQL persistence across 9 normalized tables.

erDiagram CATEGORY ||--o{ PRODUCT : "contains (1:N)" STORE ||--o{ STORE_INVENTORY : "maintains stock (1:N)" PRODUCT ||--o{ STORE_INVENTORY : "stocked in (1:N)" CUSTOMER ||--o| CARTS : "owns active (1:1)" STORE ||--o{ CARTS : "selected at (1:N)" CARTS ||--o{ CART_ITEMS : "contains (1:N)" PRODUCT ||--o{ CART_ITEMS : "added to (1:N)" CUSTOMER ||--o{ ORDERS : "places (1:N)" STORE ||--o{ ORDERS : "fulfills (1:N)" ORDERS ||--|{ ORDER_ITEMS : "contains (1:N)" PRODUCT ||--o{ ORDER_ITEMS : "ordered in (1:N)" CATEGORY { varchar id PK varchar name varchar description } PRODUCT { varchar id PK varchar sku UK varchar name varchar category_id FK decimal price boolean is_active } STORE { varchar id PK varchar code UK varchar name varchar city varchar address varchar phone boolean is_active } STORE_INVENTORY { varchar id PK varchar store_id FK varchar product_id FK int quantity_available int quantity_reserved int reorder_threshold } CUSTOMER { varchar id PK varchar first_name varchar last_name varchar email UK varchar phone varchar address } CARTS { varchar id PK varchar customer_id FK varchar store_id FK timestamp created_at timestamp updated_at } CART_ITEMS { varchar id PK varchar cart_id FK varchar product_id FK int quantity timestamp created_at } ORDERS { varchar id PK varchar order_number UK varchar customer_id FK varchar store_id FK varchar status varchar fulfillment_type decimal total_amount } ORDER_ITEMS { varchar id PK varchar order_id FK varchar product_id FK int quantity decimal unit_price decimal subtotal }
Omnichannel Architecture Invariants:
  • Store-Level Stock: Inventory is maintained by (store_id, product_id) with a unique constraint, preventing centralized stock discrepancies.
  • Oversell Prevention: quantity_available >= 0 check constraint ensures atomic reservation at the database level.
  • Persistent Shopping Cart: Active carts and line items are stored in CARTS and CART_ITEMS with a 1:1 customer constraint, enabling cross-device sync.
  • Order Attribution: Every order links to both a customer_id and a fulfilling store_id for localized pickup/delivery.
  • Historical Accuracy: ORDER_ITEMS captures the purchased unit_price snapshot independently of future catalog price changes.

GeeksforGeeks Peter Chen Notation Rules:
  • ▭ Single Rectangle: Strong Entity (independent primary key, e.g. CUSTOMER, PRODUCT).
  • ⧉ Double Rectangle: Weak Entity (depends on owner entity, e.g. ORDER_ITEMS, CART_ITEMS).
  • ⬡ Diamond: Relationship set (e.g. PLACES, STOCKS, FULFILLS). Never drawn as a hexagon!
  • ⬭ Ellipse with Underline: Primary Key attribute (e.g. id).
  • ◌ Dashed Ellipse: Derived attribute (e.g. total_amount, subtotal).
  • ⬭⬭ Double Ellipse: Multivalued attribute (e.g. phone).
  • ══ Double Line: Total participation constraint.
